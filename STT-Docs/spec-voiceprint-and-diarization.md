# EchoNote — 話者分離 仕様書

**バージョン**: 2.0
**作成日**: 2026-05-29（v1.0）／改訂: 2026-05-29（v2.0）
**ステータス**: ドラフト（実装着手前）
**関連**: `design.md` v3.0, `requirements.md` v2.0

> **v2.0 変更点**: 声紋登録を初期スコープから外し、**話者分離 + 手動ラベル修正**
> を主軸に再構成。声紋登録は「§11 将来検討」に格下げ。理由は §1.4 参照。

---

## 1. 概要と目的

### 1.1 背景

有料化（v1.0.2）リリース後、Premium プランの主要差別化機能として **話者分離**
を追加する。話者分離は会議・インタビュー・複数人録音で最も「使えない」と
言われがちな領域であり、Free 版との体験差を最も強く打ち出せる機能である。

文字起こしの各セグメントに `話者A / 話者B / 話者C` のような話者ラベルを付与し、
発話量降順で命名する。ユーザは任意のセグメントを長押しして `あなた` や
`山田さん` などの任意ラベルに rename でき、同一クラスタは一括更新される。

### 1.2 目的

| 目的 | 達成基準 |
|---|---|
| Premium への課金動機を強化 | Free ユーザが話者分離プレビューで paywall に到達する率 |
| 多人数録音の体験向上 | 文字起こしに話者ラベルが付与され、ノート生成にも反映される |
| ユーザ識別を軽量に実現 | 録音後に1タップで「あなた」を指定できる UI |

### 1.3 スコープ外（将来検討）

- 複数録音をまたぐ「あなた」自動識別（→ 声紋登録: §11）
- 複数人の声紋登録（家族・同僚など特定話者の事前登録）
- リアルタイム話者分離（録音中のライブラベル表示）
- 話者ごとの感情分析・発話量分析

### 1.4 声紋登録を初期スコープから外した理由（v1.0 → v2.0）

中立的な技術評価の結果、**声紋登録は話者分離の精度に寄与しない** ことが
明確になった。

- Diarization（話者分離）の品質はクラスタリングアルゴリズム + embedding
  モデル + VAD で決まる。声紋登録はクラスタリング結果を変えない
- 声紋登録の効果は「クラスタを `話者A` ではなく `あなた` と呼ぶ」だけ
- 同じ UX は**録音後に1セグメント長押し → 「これは私の声」タップ**で実現可能
  （同一クラスタは一括 rename）

声紋登録が本当に必要になるのは「複数録音をまたいで `あなた` を一貫させたい」
場合のみ。それは現時点では推測的需要なので、ユーザ要望が出てから追加する
（§11）。

## 2. Free / Premium マトリクス

| 機能 | Free | Premium |
|---|---|---|
| 文字起こし | ✓ | ✓ |
| 話者分離 | プレビュー（最初30秒） | ✓ 全体 |
| 話者ラベル手動修正 | プレビュー範囲のみ | ✓ |
| 話者ラベルを使ったノート生成 | ✗ | ✓ |

**設計意図**: Free にも「30秒だけプレビュー」を出すことで、話者分離の価値を
体感させてから paywall に誘導する。

## 3. ユーザフロー

### 3.1 話者分離フロー（既存の文字起こしフローへの追加）

```
録音完了
 └─ /v1/transcribe 呼び出し（変更）
    ├─ Free → 最初30秒のみ話者ラベル付与（previewSpeakers）
    └─ Premium → 全体に話者ラベル付与
       ├─ proxy 内部で diarization パイプライン起動
       └─ 発話量降順で「話者A/B/C」を割当
 └─ 文字起こし画面
    ├─ 各セグメントに話者ラベル表示（色分け + ラベルチップ）
    └─ ヘッダに「話者数: 3人」サマリ
```

### 3.2 ラベル手動修正フロー

```
文字起こし画面
 └─ セグメントを長押し
    └─ アクションシート表示
       ├─「これは私の声」 → クラスタを「あなた」にrename
       ├─「ラベルを変更」 → 任意のテキスト入力（例: 山田さん）
       └─「キャンセル」
 └─ 確定すると同 clusterId のセグメントが一括更新
    ├─ アプリ内ストアに speakerOverrides として保存
    └─ /v1/sessions/{id}/speaker-label に POST（proxy 側にも反映）
```

セッション内で完結する。次の録音には引き継がない（それは §11 の領域）。

### 3.3 ノート生成フロー（既存への変更）

```
[ノート生成] タップ
 └─ テンプレ選択
    ├─ 標準（全体要約）
    ├─ 話者別に要点（Premium）
    ├─「あなた」発言のみ要約 ← ユーザが「あなた」をrename済みのときのみ表示
    └─ 議事録形式
 └─ /v1/generate-note 呼び出し
    ├─ 話者ラベル付き transcript を送信
    └─ プロンプト分岐
       ├─ 既定 → 既存通り全体要約だが話者を意識した文体
       ├─「あなた発言のみ要約」 → ユーザが指定したクラスタの発話に絞った要点
       └─「話者別に要点」 → 話者ごとにセクション分け
```

## 5. データモデル

### 5.1 Cloudflare KV — 新規キー

なし（v2.0 で `user-voiceprint:*` は削除）。

### 5.2 既存 KV キーへの影響

- `user-tier:{deviceId}` — 変更なし
- `usage:{deviceId}:{YYYY-MM}` — 変更なし
- `session-speaker-labels:{deviceId}:{sessionId}` — **新規**。手動rename の永続化先
  ```
  {
    "spk_0": "あなた",
    "spk_1": "山田さん"
    // ラベル未変更のクラスタはエントリなし → デフォルトの「話者A/B/C」を使う
  }
  ```
  TTL: なし。サイズ: <1 KB。アプリ側ストアの真実コピーとしても機能する。

### 5.3 App 側ストア

`stores/sessionStore.ts` に追加（または `stores/speakerLabelsStore.ts` 新設）:

```ts
type SpeakerLabelOverrides = Record<string /* sessionId */, Record<string /* clusterId */, string /* label */>>;
```

ローカル真実 + サーバ KV 真実の二重保管（オフライン編集対応）。同期は
write-through: rename 時に即 POST、失敗したらキューに積んで再送。

### 5.4 文字起こしセグメントへの拡張

`types/session.ts` の `TranscriptSegment` に追加:

```ts
type TranscriptSegment = {
  // ... 既存フィールド
  speaker?: {
    label: string;       // 表示用: "話者A" | "あなた" | "山田さん" など
    clusterId: string;   // diarization 出力の元ID（"spk_0" など）
    confidence: number;  // 0..1（diarization 出力）
  };
};
```

`label` はサーバが diarization 直後に付ける既定値（`話者A` 等）。アプリは
`speakerLabelsStore` の override を優先して表示する（サーバラベルは fallback）。

既存セッションは `speaker` フィールドが欠落していてよい（Free ユーザの過去
セッションには付与しない）。

## 6. API 契約

### 6.1 POST /v1/transcribe  （拡張）

レスポンスに `segments[].speaker` フィールドを追加（Premium / Free プレビュー）。

**Response 200（Premium 例）**:
```json
{
  "text": "...",
  "segments": [
    {
      "startTime": 0.3,
      "endTime": 4.2,
      "text": "今日の議題は...",
      "speaker": {
        "label": "話者A",
        "clusterId": "spk_0",
        "confidence": 0.91
      }
    }
  ],
  "speakers": [
    { "label": "話者A", "clusterId": "spk_0", "totalDurationMs": 142000 },
    { "label": "話者B", "clusterId": "spk_1", "totalDurationMs": 98000 }
  ],
  "_quota": { /* ... */ }
}
```

**Free のレスポンス**:
- 全体の文字起こしは既存通り返す
- `previewSpeakers` として最初30秒分の `segments[].speaker` のみ含める
- 30秒以降のセグメントには `speaker` を付けない（UI で paywall プロモを表示）

**処理（Premium）**:
1. 文字起こし（Grok）と並列に diarization API（HF pyannote等）を呼ぶ
2. diarization 出力のクラスタごとに発話量を集計し、降順で「話者A/B/C」を命名
3. 文字起こしセグメントの時間レンジを diarization セグメントとマッチさせて
   `speaker` フィールドを付与

### 6.2 POST /v1/sessions/{sessionId}/speaker-label  （新規）

セッション内のクラスタに対する手動ラベルを保存する。

**認証**: 既存 HMAC

**Request**:
```json
{
  "clusterId": "spk_0",
  "label": "あなた"  // 空文字 or null で override 削除
}
```

**Response 200**:
```json
{
  "sessionId": "abc-123",
  "labels": {
    "spk_0": "あなた",
    "spk_1": "山田さん"
  }
}
```

冪等。同一 clusterId への上書きは新しい値で置換。

### 6.3 GET /v1/sessions/{sessionId}/speaker-label  （新規）

セッションの override 一覧を取得（オフライン → オンライン復帰時の同期用）。

**Response 200**: `{ "labels": { "spk_0": "あなた" } }`

### 6.4 POST /v1/generate-note  （拡張）

リクエストに `speakerHint` を追加可能:

```json
{
  "sessionId": "...",
  "template": "speaker-summary" | "user-only" | "standard" | "minutes",
  "speakerHint": {
    "userClusterId": "spk_0",        // "user-only" のときに参照
    "labels": { "spk_0": "あなた", "spk_1": "山田さん" }
  }
}
```

プロンプト分岐:
- `user-only` → `userClusterId` のセグメントだけを抽出して要約
- `speaker-summary` → 話者ごとにセクション分けして要約
- それ以外 → 既存ロジック（ただし話者情報があれば自然に文中で参照）

`userClusterId` は **手動 rename で「あなた」が指定されたクラスタID**。
指定がなければ `user-only` テンプレは選択不可（UI で disabled）。

## 7. Premium 強制ポイント

| 操作 | 強制方法 |
|---|---|
| `/v1/transcribe` の話者付与 | tier=premium なら全体、Free は最初30秒のみ `previewSpeakers` 出力 |
| `/v1/sessions/{id}/speaker-label` | tier=premium のみ受理。Free は 402 `PREMIUM_REQUIRED` |
| `/v1/generate-note` の `user-only` / `speaker-summary` テンプレ | tier=premium のみ受理。Free は 402 `PREMIUM_REQUIRED` |
| アプリ UI でのテンプレ選択肢 | `useSubscription().isPremium` で非Premium ユーザは disabled+鍵アイコン |
| アプリ UI でのラベル長押し | Free でもプレビュー範囲（最初30秒）内のセグメントのみ rename 可能 |

## 8. エラー / エッジケース

### 8.1 話者分離

| ケース | 挙動 |
|---|---|
| 1人だけの録音 | クラスタ1つ → `話者A` のみ表示。「話者数: 1人」サマリ |
| 同性・同年代の話者 | diarization の confidence 低下。confidence 0.5未満のセグメントは speaker 省略（白いまま） |
| 録音が極端に短い（< 10秒） | diarization をスキップして単一話者扱い |
| diarization API 失敗 | 文字起こしは返す（既存通り）。`segments[].speaker` は省略。クライアントは「話者分離に失敗しました」をトーストで表示し、リトライボタンを出す |
| 同一クラスタが分裂（diarization の誤り） | ユーザが手動rename で同名にすれば実質マージされる（cluster は別だが label は同じ） |

### 8.2 手動ラベル修正

| ケース | 挙動 |
|---|---|
| オフライン中の rename | ローカルストア即反映 + 送信キューに積む。オンライン復帰時に POST 再送 |
| 同一セッションを別端末で開いた | 起動時に GET で同期。ローカルとサーバが衝突したら **新しい updatedAt 勝ち** |
| 空文字 / null で送信 | override 削除（既定の `話者A` に戻る） |
| `あなた` 以外の任意ラベル | 長さ20文字まで。絵文字可。改行・タブは除去 |

## 9. プライバシー / コンプライアンス

- v2.0 では声紋データを扱わないため、追加のプライバシー申告は不要
- diarization は proxy で行うが、proxy は既存の `/v1/transcribe` と同じ
  プライバシー水準（音声データは処理後破棄、ログには載せない）
- 手動ラベル（`山田さん` 等の実名が入る可能性）は session-scoped KV に保存。
  - DELETE エンドポイントは設けないが、セッション削除時に対応する
    `session-speaker-labels:{deviceId}:{sessionId}` も削除する

## 10. 実装フェーズ

### Phase 1 — 話者分離パイプライン（推定 1〜2週間）

- proxy: diarization API 連携（HF pyannote-audio または同等）
- proxy: `/v1/transcribe` 拡張（Premium 全体 / Free プレビュー）
- proxy: クラスタ命名ロジック（発話量降順で `話者A/B/C`）
- app: `types/session.ts` の `TranscriptSegment` 拡張
- app: 文字起こし画面で話者ラベル表示（色分け + ラベルチップ）
- app: Free 用プレビュー UI（30秒以降は paywall プロモ）
- テスト: 既知の多人数音声で diarization 精度を測定

### Phase 2 — ラベル手動修正 + ノート生成連携（推定 1週間）

- proxy: `/v1/sessions/{id}/speaker-label` 実装（POST/GET）
- proxy: `/v1/generate-note` 拡張（speakerHint + 新テンプレ）
- app: ラベル長押し アクションシート + テキスト入力モーダル
- app: `speakerLabelsStore` 新設（オフライン対応）
- app: ノート生成画面にテンプレ選択 UI
- app: 「あなた発言のみ」「話者別」のテンプレ表示制御

### Phase 3 — 観測 + 微調整（推定数日）

- proxy: diarization レイテンシ / クラスタ数分布のメトリクス出力
- app: 「話者分離 ON/OFF」設定の検討（重い録音ではユーザ側で無効化したい場合）
- 実利用ログから confidence 閾値とプレビュー時間（30秒）を再校正

## 11. 将来検討 — 声紋登録

声紋登録は **複数録音をまたぐ「あなた」自動識別** が必要になったときに
追加する。ユーザ要望が出てから着手する。

実装するなら方針は v1.0 仕様の §6.1〜§6.3 をそのまま流用可能:
- `POST/GET/DELETE /v1/voiceprint`
- 外部 embedding API（HF Inference 等）
- `user-voiceprint:{deviceId}` を KV に保存（embedding のみ）
- `/v1/transcribe` の Premium パスで声紋一致したクラスタを自動で「あなた」に
  rename（手動rename より優先度低、ユーザが手動指定済みなら手動を優先）

判断基準（着手シグナル）:
- 「毎回録音のたびに『これは私の声』を押すのが面倒」というユーザ要望が
  サポートチャンネルで複数件出る
- 月10セッション以上を録音するヘビーユーザの割合が一定以上になる
